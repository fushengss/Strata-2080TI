Preparation and contention issues to handle explicitly
1. reserve_uploads is not a blanket no-allocation guarantee. prefill.cpp:7835–7849 reserves each up_ring to T*K*4 (and pageable PLE size). That covers draft tokens T*4 and16-byte bounds for the same C, but generate.cpp:17524 currently only logs reserve failure and continues. A strict concurrent candidate should fall back serial on preparation failure; PinnedRing::acquire (include/strata/core/pinned_ring.hpp:47–74) may otherwise cudaFreeHost/cudaHostAlloc/create events on the reader thread.
2. draft_kv contains no direct temporary CUDA allocation/free, but mmq::Context::run uses a caching allocator: src/prefill/ggml_cuda_host.cu:121–132 cudaMalloc on a size miss. Its host mutex protects the pool and each Prefill context/stream is separately owned, so this alone is not a proven corruption bug. It is first-use/shape-change driver-stall risk. Prefill zero-copy bounds allocate at prefill.cpp:5202–5209, and Gemm's FP16 weight cache can allocate lazily at gemm.cu:1436–1441. Current reserve_uploads does not prepare those. Verify cold-first-use, largest planned chunk and small tail shapes. After closing the pre-launch PLE-flag dependency described below, under verified all-stage all-resident graphs, no loans/pending adaptation, and the dedicated CUDA-free bell thread, these lazy allocations are performance/barrier risks rather than an independently established remaining deadlock or corruption. It is reasonable to test the narrow candidate without a large allocator-prewarm rewrite; add preparation/freeze work only for measured stalls. Never claim allocation-free. Do not claim allocation-free from the draft_kv body alone.
3. PLE is thread-safe but can serialize: src/kernels/ngram.cpp:239 has a recursive mutex; gather_batch:625 and gather_raw_iq4nl:714 hold it over a whole prompt gather. Slot PLE setup can wait there. First measure stage0 host-setup/PLE wait while overlapping; if material, a later change can shorten immutable-mmap gather lock duration or use bounded host gather blocks. Do not remove the mutex from direct I/O/cache modes.
4. Device/host synchronizations remain: draft_kv waits owner mtp.idle then its own m.cs; checkpoint callbacks and admission copies also wait. Verify batch_serve:5039 has no per-layer host doorbells on the all-resident path, except a host PLE flag; preserve the dedicated CUDA-free doorbell thread AND add the narrow early PLE publication described below; the thread alone does not cover a graph launched before b_running is published.
5. Eligibility should require actual all-stage residency, no lent expert slots / own prefill buffers, independent slot sessions, stable source, text-only and supported KV/drafter paths. Do not infer this merely from free VRAM or one primary-stage residency boolean. Keep prefill-help/DMA/helper/recycling-source exclusions. Do not permit running cache adaptation or weight replacement during the reader: pa_due includes in_prompt_read at generate.cpp:15101–15112, but entry must also have settled prior pending adaptation.
6. Cancellation/BYIELD: the reader only observes stop_at_chunk at a safe chunk boundary, then joins/drains before partial state is parked (generate.cpp:17653–17740). Resident BSTOP still passes through pump. Preserve this order and ReadEnd/Doorbells RAII cleanup on errors; never recycle the admission slot while its state/copies are still live.

Fallback if full overlap causes excessive contention
Use per-stage bounded scheduling at a layer/chunk event boundary, retaining the prompt's existing state, chunk plan, successor future and handoff ownership. Stop enqueueing further prefill on that stage when decode has waited beyond its budget; let a decode window complete; resume the same prompt without a global pipeline reset. Bound the amount of prefill already queued (a stream priority cannot preempt an arbitrarily large queued/active operation). This requires explicit event/ownership handshakes per stage and must not await all eight stages before each decode slice. It is a larger engine change; do not implement it by deleting drain_pipeline or repeatedly calling sp.run on tiny pieces. If immutable-mmap PLE locking is the actual limiter, fix that host bottleneck before introducing this scheduler.

Author-plan review addendum: confirmed pre-launch PLE deadlock window
The author identified an additional dependency; independent inspection confirms it. Earlier provisional confidence that residency plus a dedicated bell thread eliminated every driver-lock cycle was incomplete. Current code: stage_batch gathers PLE (verify.cpp:4652–4669), then resets h_flag to0 (4683). batch_launch_rows launches its body graph at4359, then another save graph/head/query before b_running=true at4369. The resident graph still executes wait_flag_ge(m_flag,1) at1504. If the reader enters cudaMalloc/device synchronization after that first launch, the driver can wait for the graph while the main pump blocks in the next CUDA call. batch_serve5035 returns immediately while b_running is false, so the separate bell thread cannot publish the PLE flag. This is a concrete circular dependency allowed by the call order, even with every expert resident. Existing early_ple_flag_mode3334–3342 is a solo launch path and does not protect batch_launch_rows. No new GPU deadlock was induced by this review.

A minimal fix is justified: only for the explicit new narrow overlap mode and a refreshed all-resident PLE-owning stage, publish h_flag=1 after successful PLE gathering and the normal resets, with seq_cst plus strata_store_fence before publication, before the first graph launch. This matches the existing solo early-publication visibility protocol; it does not change PLE values or default/nonresident execution. stage_batch's end or immediately before the first batch graph is suitable provided capture_deferred does not clear the flag (none found). Do not move b_running=true earlier: that exposes partially initialized window metadata to batch_serve. Failure paths may leave an unused raised flag; the next stage_batch resets it, and launch errors retain existing fatal cleanup.

With that prerequisite, the author's proposed first version (resident-only opt-in, own buffers/no loan, settled adaptation, retain existing whole reader+pump, pinned reserve failure falls back serial) is a reasonable isolated experimental scope. No additional prefill-to-pump circular mutex dependency was found in reviewed paths. PLE gather holds its mutex over host work/I/O and can delay decode setup, but does not require a main-pump callback to release it. MTP head enqueue records the source event before target waits and target completion records before source waits (mtp_head.cpp245–254); P1 target head follows recorded-event order (decode_head.cpp301–329), so those cross-device edges do not require a future unqueued host producer. This is static review, not a runtime pass. Lazy allocations need not demand a broad allocator rewrite once the known graph/host dependency is removed, but their first-use effects must be measured.
