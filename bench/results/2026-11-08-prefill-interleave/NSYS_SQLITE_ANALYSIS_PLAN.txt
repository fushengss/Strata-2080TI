Per-card measured quantities
For each engine device, clip each kernel [start,end) to the selected wall interval; merge overlapping and touching intervals. Report kernel interval union duration/window duration, aggregate kernel duration (can exceed wall time), kernel count, union idle intervals, largest idle gap and idle total. Also compute memcpy and memset intervals separately, then union(kernel,memcpy,memset) for traced activity coverage. Copy-engine work is not SM activity. Avoid summing individual stream busy percentages or interpreting any interval fraction as FLOPs, occupancy, achieved memory bandwidth or a limit of the hardware. Check missing card versus zero observed work explicitly.
For cross-card activity, sweep the merged intervals to get durations with0..8cards executing kernels and all-card idle spans. Report per-card windows and counts so one busy device cannot hide pipeline bubbles on another. At most bounded numeric gap records are needed for review; kernel text is not needed to calculate coverage.

Launch and synchronization interpretation
Only after real schemas establish keys: connect engine CUDA runtime/driver API rows to GPU kernel/graph nodes by verified process+correlation and graph/node identifiers. CUDA graph launches may map one API to many nodes; do not force a one-to-one join. Report matched/unmatched/ambiguous correlation fractions and do not derive host launch latency when mappings are ambiguous or APIs start outside capture. Kernel start minus API end may be negative when asynchronous work starts before API returns; preserve/report this rather than clamp and call it wait time. Count/union host API blocking durations per engine thread; resolve only needed CUDA API names via StringIds after exact IDs are selected, never dump the string table.
For a GPU idle interval, 'no observed submitted work', long host synchronization call, and queued dependency wait are different hypotheses. Submission timing and valid graph relationships may support a narrower explanation; gaps alone cannot prove cause. OSRT calls can add evidence for host blocking, but CPU sampling/ctxswitch are disabled, so absence of an API call does not identify CPU scheduling cause. Per-stage overlap requires proven graph/kernel stage mapping, not just cards concurrently busy.

Reporting boundary
Final report: exact identities and actual window, per-GPU kernel/copy union and largest gaps, cross-card active-count distribution, valid host-call/correlation evidence, and explicit unavailable fields. C8 primarily diagnoses decode scheduling; it does not by itself prove long-prefill overlap. No speedup claim, no universal100%GPU target, and no output token rate inferred from kernel count.
