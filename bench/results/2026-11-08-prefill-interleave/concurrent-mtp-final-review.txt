Resolved review finding

PleWeights::key_native_q8_1 is writable, despite being stored in the shared weight descriptor: generate.cpp:5506 wires it to wk->native_q8_1; kernels/cuda/ple.cu:313 quantizes into it. The prefill fallback (prefill.cpp:4031) and verifier fallback (verify.cpp:1591) could write it concurrently when the native quantized key route is active without a BF16 key. Final commit e895aa44 adds a conservative check at prefill.cpp:7850–7859: every actual PLE stage with that native-key route declines concurrent preparation before reserve/allocation and takes the existing serial path. Lifetime, fallback and cancellation
- MTP strict_uploads is an optional parameter preserving existing callers. Reservation failure returns false before reader creation; prompt upload/workspace preparation failure also takes serial fallback. Partial preparation leaves owned allocations attached to their normal object lifetime, not stack pointers used by a reader.
- The existing ReadEnd RAII joins the reader before clearing its stop hook and in_prompt_read. Doorbells RAII stops/joins the CUDA-free service thread before disabling external service. Normal completion joins the reader, clears the hook, then drains/settles decode before admission state is copied/reused. The new measurements do not change this ordering.
- Resident BSTOP is consumed on the pump thread. BYIELD requests a safe prefill chunk boundary; it is not immediate kernel preemption. Cancellation of the injected request can leave the reader finishing its current whole run unless a yield is requested. Neither the source nor the test report should claim immediate GPU cancellation. Existing fatal launch/read error handling is retained; this review does not establish recovery from a sticky CUDA failure.
- Default-off execution retains the original workspace selection, split-MTP exclusion and reservation behavior. Enabling the new flag also requests high-priority verifier streams during initialization, even when a particular read falls back or runs alone. Therefore solo prefill must be measured with the flag enabled; eligibility fallback alone does not prove zero performance impact.

Measurement interpretation and required qualification
The new end record counts native BT tokens from completed pump calls observed before reader done publication; it excludes the ambiguous final pump and final drain. It includes native terminal-token accounting and is not API content tokens, accepted drafts alone, verification rows or a per-GPU overlap measurement. A positive count with a paired successful read, expected active-slot/residency/private-buffer counts and successful completion is evidence of decode progress during the reader interval. It is not a speedup by itself.

Before considering deployment, run the frozen same-binary flag off/on correctness and performance comparison, including:
1. First-use overlap and warmed overlap, planned full chunks and a small tail; exact completed greedy/seeded output, usage and finish behavior.
2. Resident cancellation, injected-reader cancellation/BYIELD, slot reuse/continuation, no timeout/CUDA error, and complete cleanup.
3. Solo cold/warm100K read_ms and TTFT; mixed injected long-prompt read/TTFT as well as resident phase-clipped gaps, fairness and completed API throughput. Keep layer split/chunk/prefill settings unchanged. A reader begin/end log alone is insufficient.
4. Confirm the eligible route actually ran with all stages resident/private and native reader-interval tokens advanced; fallback runs cannot establish overlap benefit. Reverse order or repeats are needed before interpreting small changes.
5. Treat GPU activity/in-flight counts as their actual measured quantities, not FLOPS occupancy or a promise of100% utilization. PLE lock contention, lazy allocation, checkpoint sync and final admission copies remain plausible shorter gaps requiring measured attribution.
