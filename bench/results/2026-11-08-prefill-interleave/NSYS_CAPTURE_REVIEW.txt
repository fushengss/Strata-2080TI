Attach/reload decision
There is no established arbitrary PID CUDA attach mode in the supplied profile/launch/start/stop help. --start-later delays collection of a process launched under Nsight; it is not attach. If the current engine already belongs to an owned nsys-injected session, start/stop it without reloading. Otherwise defer capture until the next separately justified diagnostic restart; do not restart merely to satisfy this review and do not profile the timed A/B process. NVIDIA's release notes also document the Linuxx86_64 GUI attach limitation; newer current CLI features must not be assumed present in2025.3.2.

Minimal capture
Use the argv templates in nsys-capture-review.json. launch sets trace=cuda,osrt, cuda-graph-trace=node, cuda-event-trace=false, osrt-threshold10000ns and wait=all. start sets sample=none and cpuctxsw=process-tree; these options on launch are deprecated in this installation. Keep CUDA event trace off: installed help warns it adds overhead and may create false cross-stream dependencies. Do not enable GPU metrics, CPU sampling/backtraces, Python tracing, memory usage/page-fault collection, STRATA_VERIFY_PROFILE, STRATA_MTP_PROFILE, P3events or extra P4 per-window output in the first capture. Their interference is not needed to answer whether decode and prefill coexist.

After model ready, establish four synthetic resident outputs. Complete nsys start, record monotonic+wall timestamps and the own request IDs, then inject exactly one fixed synthetic actual~52k prompt. A bounded12–15s node-level capture should contain insertion and much/all of the baseline10s read; never assume coverage if the instrumented read is longer. Stop in a timer/finally, let requests finish/cancel cleanly, then export/analyze offline. This is one separate diagnostic, not evidence for optimization percentages. If proof from route counters+untraced A/B is already sufficient, skip Nsight. No automatic shutdown or kill command is proposed; root retains ownership of session cleanup.

Secrets/content handling
Use loopback/authenticated isolated synthetic requests, existing key read from a0600 config into the client memory, and a0700 capture directory. Do not put key/prompt/output in argv/env/NVTX labels. --show-output=false is NOT a privacy switch: installed launch help says it still stores stdout/stderr inside the report. If server logs must stay out of the report, launch a private shell wrapper that redirects the server stdout/stderr to separate private files BEFORE exec of the Python server. Keep the engine's stdin/stdout protocol connected normally via the server. Pass config path, never key value. Disable external traffic for the diagnostic; the child process trace otherwise includes unrelated requests. Check generated report/log metadata for credential strings before sharing; share numeric derived tables, not the raw bundled report by default.

What the trace can establish
1. Identify actual engine PID/context and every GPU's streams; require nonempty CUDA API and GPU rows for all relevant cards. Python-only trace or empty kernel tables is a failed capture.
2. Use CUDA correlation IDs, graph IDs and launch threads to separate verifier/MTP/target-head graphs submitted by the pump from uncaptured prefill kernels submitted by the reader/stage worker threads. Check shape/kernel names and known source devices as supporting evidence. Same kernel name alone cannot classify a request.
3. For each GPU and the SAME capture subinterval, merge kernel execution intervals before computing active-union time; compute gaps and overlaps between identified decode and prefill streams. Do not sum kernel durations or cross-GPU percentages. Graph lifetime alone includes event/host waits, so node-level execution is needed before calling an interval GPU-active.
4. Correlate long idle gaps with absence/delay of launch APIs, cudaMalloc/cudaFree/host-allocation or synchronize calls, OS mutex/thread scheduling, copy engines and cross-device event dependencies. Those give hypotheses for host submission, allocation barriers, PLE lock contention, handoff/PCIe or stage imbalance; a long CPU call alone is not causal proof.
5. Relate only owned SSE numeric timing/usage and concurrent-route counters to the trace window. Graph/node instrumentation changes schedule and throughput; report an observed overlap and candidate stall cause, not uninstrumented performance gain, SM occupancy, FLOPS or a promise of GPU100%.
