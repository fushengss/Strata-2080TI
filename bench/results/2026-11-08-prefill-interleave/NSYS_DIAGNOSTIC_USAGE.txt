Capture behavior:
- The whole model load is injected but collection starts later, via installed2025.3.2 nsys launch/start/stop. This is not arbitrary-PID attach. No CUDA-profiler or NVTX hooks are added.
- C8 uses the unchanged frozen c8_check workload,1024tokens each, and an in-process Client subclass only to observe readiness. Start is requested after all8streams have a first output and are still active. Its original completion/exclusivity/overlap gates remain.
- Mixed uses unchanged finite primary bodies, prompts, sampling, budgets, calibration and phase schedule. It requests capture on the existing second-injection stdout marker immediately before the calibrated~60k injection. The workload is not paused for nsys startup; the earliest part of admission may precede collection. This is intentionally a diagnostic, not a modified timed harness.
- Stop is requested12..15seconds after the nsys start request (or earlier if the entire workload ends). Start-request/return and stop-request/return wall+monotonic times are saved. Export/flush time is separate; the report establishes actual collected bounds. There is no claim that the full long read fits the window.
- Frozen workloads finish normally after collection stops; on error/interruption the helper closes only its owned server/processes. It never resumes production automatically. A failed fixture or capture remains failed even if a partial trace exists.

Trace configuration, checked against the saved installed help:
  launch --trace=cuda,osrt --cuda-graph-trace=node --cuda-event-trace=false --wait=all --show-output=false
  start --sample=none --cpuctxsw=none --output=<new private prefix>
No CPU samples/context switches, GPU metrics, memory tracing or extra engine profiling flags are enabled. OSRT still records runtime calls; scheduling causality cannot be established without a separately justified context-switch trace. Node tracing itself can substantially alter schedule/latency, so this capture supplies no performance percentage, token-rate comparison or saturation claim.

Privacy/ownership:
The private shell redirects server stdout/stderr BEFORE Python/server startup. --show-output=false alone would still package output into nsys reports and is not relied on for privacy. Only a small noncredential environment allowlist is inherited; API keys never enter argv/env/NVTX. The output directory is0700 and files0600. The server wrapper records PID+birth tick, and cleanup signals those exact known server/engine identities only. A repeated SIGINT/SIGTERM during cleanup is ignored so it cannot skip config deletion. GPU power/clocks/governors are not changed.

receipt.json contains safe config identity, startup/actual binary+library-map checks, requested capture times, actual workload coverage, native reader numeric evidence, own cleanup status and a temporary-key byte scan. The byte scan is not a decoder for compressed report payloads: keep raw nsys/server/client artifacts private. Only synthetic requests are issued, but the C8 frozen client includes synthetic bodies/outputs in its private result files. Share derived numeric tables, not the raw bundled report by default.

Interpretation gate after a real capture:
Require nonempty engine CUDA API and GPU kernel rows on all8relevant cards, not Python-only activity. Resolve graph/node correlation IDs and launch threads before separating verifier/MTP/target-head streams from reader/prefill streams; identical kernel names alone are insufficient. For one common bounded interval, merge kernel execution intervals per GPU, measure idle gaps and simultaneous decode/prefill activity, and inspect launch gaps, allocations, synchronization and copies near stalls. Summed kernel time or graph lifetime is not GPU active-union time, SM occupancy or FLOP utilization. The helper intentionally does not auto-export with unverified nsys export CLI or invent a SQLite schema; inspect the actual report first, then export/analyze using that installed tool's help.
