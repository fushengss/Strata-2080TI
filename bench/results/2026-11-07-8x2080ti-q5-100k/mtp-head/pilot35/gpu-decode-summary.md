# Pilot35 decode 区间 GPU 采样

仅对已保存数据做 CPU 分析，没有调用 GPU 或服务。结果来自一次 off/on pilot，不代替正式 ABBA 的性能结论。

请求 JSON 的非空 content delta 含绝对 epoch，与 `start_epoch + ttft_s/last_content_s` 一致。GPU CSV 没有时区后缀；依据同主机 `run_abba.py` 在 `ready_epoch` 之后启动 monitor 的顺序，唯一符合 0–5 秒启动范围的时区偏移为 UTC+0。两臂首个 GPU 采样分别比 ready 晚 74.0/75.8 ms，最后一个采样分别比 finished 早 159.9/329.6 ms。没有通过利用率曲线移动时间轴。

采样请求间隔为 500 ms，实际各卡间隔中位数为 545 ms，最大间隔约 0.75 s。每个请求每卡有 9–17 个完整 decode 区间样本；另给出两端各裁 1 秒的内部区间，剩 6–13 个样本，用来检查阶段边界的影响。GPU 采样包含设备内部的统计区间，精确范围没有记录，因此裁边也不能保证完全排除前后阶段。

下面将同一 arm 的 cold-code、warm-code、cold-prose、warm-prose 四个窗口合并，按采样点等权计算；长 prose 窗口贡献更多点。off/on 的 decode 长度不同，所以样本数量不同。完整 JSON 另有逐请求、逐类别和逐卡结果。

GPU3/5 的采样利用率和功耗上升，GPU7 下降；裁边后方向一致，符合 MTP draft head 从 GPU7 分到 GPU3/5 的负载转移。其它 GPU 的变动较小。这是采样读数上的观察，不能单独证明 decode 加速由哪一段造成。

这些读数不是 SM occupancy、显存带宽或 kernel critical path。约半秒的读数不能给出瞬时峰值、逐 kernel 重叠关系、硬件满载程度或可靠能量积分；本报告没有据此做这些推断。时间边界为本机 HTTP 客户端收到内容的时刻，不是 GPU 内核开始/结束时刻。

数据：[gpu-decode-summary.json](gpu-decode-summary.json)。工具：[gpu_decode_summary.py](../gpu_decode_summary.py)。工具为新加分析脚本，八个冻结 harness 文件 SHA256 与 pilot manifest 全部一致。除实际数据核验外，错误 UTC+8 和不匹配的 first-content 时间均被拒绝。

对解包后的同格式 ABBA 目录运行：

```sh
python3 gpu_decode_summary.py --root /path/to/abba-run
```

它只读取各 arm 的 `gpu.csv`、`metadata.json`、`cold-*.json` 和 `warm-*.json`，生成额外 `gpu-decode-summary.json`。无法唯一确定时区、采样覆盖不足、内容时间戳不一致或请求不满足隔离检查时会失败；不会猜测时间偏移。
