# 网页 Decode now / ANSWER 的统计口径复核

本审计只在 CPU 上执行部署版本 `serve/server.py` 的原始 `Service._rate_of` 函数。源码 SHA256 为 `40c5e9dfc96ab208b6514bd2f5f48986afb3e01b3927f873cff8d358d62528c9`；函数、常量、32 样本 deque 的原文和行号保存在 `rate-semantics-check.json`。没有请求服务、使用 GPU、修改源码或部署修复。以下是合成时间线，不是 21:44 的现场记录。

网页的这个数字是全部在途请求速率之和，不是单请求速度。名义窗口为 2 秒，但每请求最多保存 32 个 token 采样；每路 50 tokens/s 时，实际保留的样本只跨约 0.62 秒。计算时分母为末次 token 时间减首次合格 token 时间，没有计入末次 token 到当前时刻的空白；所有近期样本过期后，又退回整个请求自首 token 起的平均速度。

用 8 路完全相同、原本每路 50 tokens/s 的已知时间线执行原函数，得到：

| 采样时的状态 | 网页合计显示 | 实际最近 2 秒合计输出 |
|---|---:|---:|
| 持续出流 | 400.00 tokens/s | 400.00 tokens/s |
| 已停止出流 1 秒 | 400.00 tokens/s | 200.00 tokens/s |
| 已停止出流 3 秒 | 360.27 tokens/s | 0.00 tokens/s |

第三行假设请求仍在途，每路首 token 距当前 30 秒、已产 1351 tokens，因此代码返回每路 `1351/30`。这证明网页显示 300–400 不足以证实同一时刻真实产出也达到 300–400；它可能是真实并发吞吐，也可能混入短窗口和停顿后保留旧速率的影响。仅凭上述 CPU 复现，不能断言 21:44 的某个具体峰值全部虚假。

分子是 token 数而非字符/字节。拒绝的 MTP 草稿和缓存 prompt 不在分子里；服务端主动插入的 thinking wrap、forced-tool opening 等 token 也进入 API generated 计数。MTP 成批输出和前端消费队列会影响短窗口到达速率，不能把它解释为 GPU 瞬时计算速度。

较新的 Terminal 大号 **ALL REQUESTS** 使用两次服务器累计输出计数的差值除以同一采样时间差，和这里的网页 Decode now / 小号 ANSWER 不是同一个算法，本复现不适用于那个数字。判断实际峰值，应优先保留这种共同时间区间的计数增量，并用较长窗口与完整请求计数交叉检查。

复现：`python3 rate-semantics-check.py`。脚本校验源码 SHA 后，AST 提取并执行原函数体，只替换 `time.time` 为固定时钟；输出同时保留原样本、分支、分母和真实 2 秒区间内的 token 数。
