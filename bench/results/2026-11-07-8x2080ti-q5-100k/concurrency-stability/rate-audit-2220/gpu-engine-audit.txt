结论

当前 8 slots / PP8 / groups8 的并发工作主要是八组请求的流水线，不是每张 GPU 同时算八请求的大矩阵。最重要的新发现是：已配置的 main head GPU2/4 只接入 solo PW2 路径；当前 batch/piped verifier 的主输出 head 仍在 GPU7。已接入并发的 offload 是 MTP draft 词表 head GPU3/5。GPU7 因此仍承担末段六层、主词表投影、各 slot 的 MTP body/KV/最终选择，以及 sampled target 的采样。

已有 head-reverse/01-on C8 同时出流区间的 GPU 审计显示：GPU0..6 平均 utilization 约 54–65%，GPU7 96.57%，GPU7 平均 248.85 W、SM 1647.5 MHz，其他卡 SM 约 1810–1860 MHz。见同目录 gpu-util-audit.*。这是末段不均衡的直接观测，与上述代码位置相符；它不能独自量化每个内核的占比，也不能仅凭功率和时钟就断言 power cap。不要将八卡平均利用率解释成每张卡都有同样比例的空闲，更不要据此承诺尚有 1/0.6 倍的性能。

主控完成的新 C8 复跑补证（本审计者未运行）：同日台北 22:40:10.195–22:40:26.801 共同出流窗口，裁两端各 1 秒后每卡 27 个采样点。GPU7 utilization 97.81%，248.91 W / enforced 250 W，SM 1688.3 MHz；sw_power_cap 27/27，SW/HW thermal 与 power-brake 均 0/27。其他卡 utilization 55.44–65.78%，只有 GPU5 间歇 sw_power_cap 4/27。API 整场 272.1246 tok/s、native batch 300.3 rows/s。见同目录 gpu-power-live-audit.json/txt。这次有 throttle reason，已直接确认窗口中 GPU7 持续受功率上限约束；仍不能从这些标量单独计算卸载某内核的收益。两种吞吐的时间区间不同，不能混作一个端到端指标。

- /Users/fu/project/HAI/Strata-decode-head/src/program/generate.cpp:14773–14774：每组 row capacity = GS * (1 + pm_drafts)。当前 pm_drafts=1，所以通常是一个请求的 current token + 一个 proposal。

- /Users/fu/project/HAI/Strata-decode-head/src/program/generate.cpp:15098、15189–15195：每 stage 同时只持有一个 stage_group；该组的 1–2 行送进 batch_launch_rows。
- /Users/fu/project/HAI/Strata-decode-head/src/program/generate.cpp:15110–15118：组必须没有旧窗口 inflight 且所有本组 draft chain 已就绪，才能开始下一轮；不就绪则尝试另一组。
- /Users/fu/project/HAI/Strata-decode-head/src/program/generate.cpp:14940–14961：新 draft 要等最后 stage 的 residual，先复制并用 event 串起 chain，随后该组才具备下一轮启动条件。

因此并非完全“没有 batching”：验证器有 multi-row kernel，MoE 调用 grouped expert kernel（/Users/fu/project/HAI/Strata-decode-head/src/core/verify.cpp:2378），PLE 投影也有 multi-row 形式（1508–1519）。但当前每组最多两个相关 token，不是八个独立请求的八行共享权重计算。all-resident 消除了专家搬入，不会消除小矩阵、数据依赖与流水线气泡。

推断：单组循环的末段/head/draft 延迟、阶段间不均衡和 ready 组数量共同限制 occupancy。不能套用训练 GPipe 的单个固定填充/排空公式来计算这条连续自回归闭环的实际利用率。

下一步优先级与正确性边界（建议，尚未实现或测得收益）

P1：把主输出 head 的分担接入 batch/piped deferred-commit verifier。
- 首先只改 decode 目标验证路径，保留原 prefill 层分配、buffer、chunk 和 admission 路径。复用已有 GPU2/4 head 权重/分片的可能性需要确认对象生命周期和 workspace；不要按 slot 重复上传整份 head。
- 当前 solo TP2 fastpath 只能合并 greedy argmax。/Users/fu/project/HAI/Strata-decode-head/src/core/verify.cpp:5326 明确排除了双 helper 的 sampled 情况。并发业务不能把 sampled target 偷换成 greedy。
- 第一版应让 helpers 计算完整词表各自分片，逐位重建原 logits，并保留原 slot_row_draw/sample_tokens 的 Philox(seed,position)、temperature/top-k/top-p、penalty/history、bias 与 nonfinite 处理。之后才讨论跨分片抽样算法；不能只交换每分片 argmax。
- 必须保持每组/每 slot 的 row 映射、saved state、accepted prefix 和最终 residual。若要在 remote head 尚未完成时释放 GPU7 body 给下一个组，要为这些数据与 logits 提供独立 workspace/event 和 pending-head 状态，避免现有 vk.final_R_all()/last_rows_/head_logits_ 被后续组覆盖。
- 验证至少覆盖 mixed sampled+greedy、MTP 接受/拒绝、cancel/reuse、预算边界、长上下文；对照完整输出/usage/finish，并验证 100k prefill 不退化。新增明确 per-path counter，防止仅看到配置就以为路径生效。

P2：将 sampled batch 的同步尾部改为异步完成状态。
- sample_rows 仍在 GPU 上执行正确原算法，但 completion 用 event/poll 分阶段收尾，不让公共 pump 在 GPU7 采样上 cudaStreamSynchronize。
- 必须保护每组采样参数、position/history 和输出 buffer 生命周期，不能为了非阻塞而读取未完成结果。这项收益需与主 head offload 分开 A/B。

P3：确认 P1/P2 后仍由 MTP body 限制，再做局部 packing 或移动 body 的评估。
- 优先研究同一 GPU7 上多个 ready slot 的 MTP body 合批以复用共享权重，或只在一个 stage 已有多个 ready group 时合并 kernel 的行。它们都需要严格保留各 slot 的 KV、position、采样和 commit 语义。
- 不应笼统把 groups8 改 groups4：固定 8 slots 会从八组变四组，行数增加但同时在八段内流动的组数减半，可能加大空泡。增加至 16 slots 同样要先核对 KV/drafter 显存和长上下文 admission 成本，不能假设专家已放下就有足够所有状态显存。
- 若移动整个 MTP body，需要处理 draft dense/expert 权重与 KV 所在设备；只加 GPU 参与并不自动产生收益。此项比主 head 接入 batch 的改动和正确性边界更大，应后置。
