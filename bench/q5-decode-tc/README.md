# RTX 2080 Ti 解锁后的 Q5 decode 算子对照

2026-11-20，`10.100.3.3`。生产配置是 Flash-Next-Uncensored Q5_K_M、8 卡分层、16 槽分 8 组、并发每槽最多一个 MTP proposal。采集实例只监听 `127.0.0.1`。路由采样只读取 piped decode 的专家 ID，保留原有 prefill 和量化权重。采集开关经 20 个 CUDA Graph 重放用例验证，resident plan 测试共 641 个用例通过。[采集入口](capture_run.py) · [采集校验](results/capture-parity.log)

## 实际专家批量

两组都通过独占及全宽度检查。每卡记录同时开始、结束于全宽稳态窗口内的 96 次 decode，覆盖所有 48 层。测试使用代码和文章的固定种子请求。[路由汇总](results/route-shapes.json) · [8 路](results/cohort8.json) · [16 路](results/cohort16.json)

| 并发 | 每次流水组验证的行数 | 专家批次总数 | 1 行 | 2 行 | 3 行 | 4 行 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 2 | 73,456 | 54,752 | 18,704 | 0 | 0 |
| 16 | 4 | 139,272 | 99,494 | 35,676 | 2,934 | 1,168 |

8 路和 16 路平均每个专家批次分别只有 1.255 和 1.323 行。当前 SM75 的 FP16 MMA 需要 8 个 token 列，因此这两个路由分布的有效列比例约为 15.7% 和 16.5%。

## Q5 专家内核

在有解锁前 cuBLAS 基线的 `04:00.0` 上，分别重放第 3、6、42、47 层的真实路由和对应的 GGUF 压缩权重。每层每个并发选 36 个路由，覆盖 Q5_K gate/up、Q5_1 或 Q8_0 down。两臂共用确定性激活，经生产代码转为 Q8_1。候选临时解包到 FP16 寄存器，用 SM75 `HMMA.1688.F32` 做 FP32 累加。第二个候选用 `half2` 做反量化，Q5_K 分块 scale 和 offset 会提前舍入到 FP16。[候选内核](tensor_expert.cu) · [重放程序](bench.cpp) · [GPU 采样](results/operator-gpu.csv)

每条路由交替运行两臂的 CUDA Graph，五轮各重放四次。表中取每条路由五轮中位数，再取该并发 144 条路由的中位数。时间包含 gate/up、SwiGLU/Q8_1 和 down，单位为微秒。

| 并发 | 生产 DP4A | FP32 解包后转 FP16 | 生产 DP4A（half2 同轮） | half2 解包 + FP16 MMA |
| --- | ---: | ---: | ---: | ---: |
| 8 | 149.50 | 430.77 | 148.96 | 538.88 |
| 16 | 290.13 | 836.54 | 287.30 | 1074.18 |

两种候选的 576 条完整路径对照全部通过成对误差阈值，最大相对 RMS 为 0.475%，无非有限值。FP16 转换没有带来完整路径的算子级胜例。单看 gate/up，常规 FP16 候选也分别是 80.06 → 341.20 和 154.31 → 673.14 微秒。[常规 FP16](results/operator.jsonl) · [half2](results/operator-half2.jsonl)

初跑的 CPU 参考对 Q8_0 down 误用了 CPU 的激活格式，导致两种候选各有 12 项参考对照误报。改用 GPU 的 Q8_1 后，在原采样位置重跑，每种候选 24 项 CPU 参考检查均通过。该修正不改变两臂的 GPU 计时。初跑另有 5 项常规 FP16、6 项 half2 在 SwiGLU/Q8_1 中间结果超过预设的最大单点误差阈值，完整专家输出仍通过原阈值。[常规 FP16 参考复核](results/operator-check-0.jsonl) · [half2 参考复核](results/operator-check-1.jsonl)

## 同实例 A/B

回环实例保留原 16 槽、8 组、MTP、KV 和 prefill 配置。两种解码模式在同一进程内切换。引擎日志确认八张卡都捕获了 FP16 decode 图。表中用服务端输出 counter 增量除以所有请求同时 decode 的有效区间，单位为 tok/s。[八卡切换记录](results/ab/attention-switches.log)

首轮的四个工作负载中，第二臂多复用了前一臂的请求前缀。首轮短提示的稳态变化为 8 路 421.50 → 435.38、16 路 542.91 → 554.99，热 100k 为 8 路 382.13 → 386.47、16 路 483.92 → 493.97。首轮整批吞吐和首字时间有额外的缓存状态差异，复测在每一臂前用相同输入预热。

冷 100k 两臂各三轮，缓存命中一律为 0，输入和输出哈希三条全部相同。原生 prefill 中位数为 11.0608 → 11.0344 秒，TTFT 为 11.2460 → 11.1274 秒。[V3](results/ab/v3-cold100k.json) · [FP16](results/ab/fp16-cold100k.json)

## 热 100k 首字延迟与稳态策略

上轮慢的 8 路请求在发出后约 0.75 秒已全部活跃，API 队列为空。V3 在 4.50 秒占满 8 槽，并在 5.25 秒进入全宽 decode。FP16 那轮分别在 12.01 和 12.51 秒才到达这两个阶段。每路增量仍是 7 token，已经占槽的请求在等待下一槽时也出现计数暂停。

快的一轮从停放的会话检查点恢复了 8 次，合计约 0.80 秒。慢的一轮有 5 次从旧请求槽取回长会话的转折点，合计约 6.26 秒，其中三次各用 1.67–1.84 秒。旧槽分支按 GPU 逐段恢复，会在每个 QSA 层保存并恢复 KV，中间有设备同步，然后还要把主会话的状态复制到目标槽。缓存选择按匹配长度比较，同长度时旧槽优先。四个热 100k 对照的第二臂都走过该慢路径，V3 和 FP16 各两次。[恢复日志摘录](results/ab/checkpoint-paths.log) · [选择缓存来源](../../src/program/generate.cpp#L16532) · [从请求槽恢复](../../src/program/generate.cpp#L14454)

稳态策略只在引擎的顶层 decode 调度中启用 FP16。输入进队列后，尚未提交的阶段切回 V3，已提交的 CUDA Graph 自然结束。准入、在读或挂起的 prompt、以及尚未完成首轮验证的活跃槽都会阻止新 FP16 提交。策略作用在引擎已收到的命令上，HTTP 仍在准备 token 且未送入引擎的请求由服务端处理。[调度策略](../../src/program/generate.cpp#L15275) · [复测程序](qsa_steady_ab.py)

复测只在 `127.0.0.1` 运行。每种宽度做两组反序成对测试，各组输入、缓存命中和用量逐路一致，命中 99,993 token。8 路读 64–68 个增量 token，16 路读 64–69 个。每路输出 768 token。表中分别取两轮的指标均值。

| 并发 | 首字中位（s） | 整批吞吐（tok/s） | 稳态吞吐（tok/s） | 稳态 SSE 间隔 p95（ms） |
| --- | ---: | ---: | ---: | ---: |
| 8 | 5.100 → 5.151 | 252.29 → 252.83 | 384.51 → 385.05 | 35.84 → 35.70 |
| 16 | 9.484 → 9.419 | 304.57 → 308.38 | 482.56 → 488.68 | 56.79 → 56.25 |

两种执行顺序里，后跑的一臂的首字和整批吞吐均较差。8 路的 slot copy 总时长在两组内分别从 1.67 和 1.93 秒增加至 2.84 和 2.80 秒。16 路分别从 3.66 和 3.90 秒增加至 5.15 和 5.31 秒。这一轮准入没有发生上次耗时 1.7–1.8 秒的旧槽转折点恢复。16 路一轮在 batch 结束后的单路尾段有一次 286 ms 的旧槽恢复。48 个固定种子的采样输出哈希有变化。[8 路复测](results/steady/w8-r1-guarded.json.gz) · [16 路复测](results/steady/w16-r1-guarded.json.gz)

在 8 路同时运行时插入第九个请求，引擎约在发出请求后 99.8 ms 因收到命令切至 V3，并在约 342.7 ms 恢复 FP16。该请求命中 99,993 token，344.5 ms 返回，九条请求全部结束。这组用于核对切换行为。[插入请求记录](results/steady/overlap.json)

### 8 路同槽位状态补测

两边各自在 V3 下先将 16 个槽置于短会话状态，再使用同一共享前缀、同一请求和种子。初次的短会话负载未占到全部槽，补测将短会话输出上限提高到 384 token，确认两次都覆盖 16 槽。两臂实际命中和用量逐路相同，每路输出 640 token，主会话复制到目标槽的累计时间为 1.534 → 1.509 秒。[短槽状态预热](qsa_steady_recheck.py) · [补测日志](results/steady/recheck.log)

| 指标 | V3 | 稳态 FP16 |
| --- | ---: | ---: |
| 首字中位数（s） | 4.827 | 4.732 |
| 首字 p95（s） | 7.877 | 7.686 |
| 整批吞吐（tok/s） | 244.63 | 242.93 |
| 稳态吞吐（tok/s） | 379.00 | 385.37 |
| 稳态 SSE 间隔 p95（ms） | 35.85 | 35.63 |
| 整批最长 SSE 间隔（s） | 0.861 | 0.857 |

同槽位补测的整批吞吐点估计低 0.69%，两轮反序对照也呈交叉。结果支持准入回退和稳态恢复，尚不足以确认整批端到端无退化。测试结束时选择恢复生产 V3。[V3 补测](results/steady/w8-r3-v3.json.gz) · [FP16 补测](results/steady/w8-r3-guarded.json.gz)

生产 Q5 按原配置和原引擎重新启动，16 槽就绪。独立核对了引擎哈希、监听地址和认证状态，两个认证接口返回 200，匿名模型列表返回 401。[执行日志](results/steady/run.log) · [线上验证](results/steady/production-verified.json)
