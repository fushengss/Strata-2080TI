# 8x RTX 2080 Ti 优化记录与后续路线

本文记录这台服务器上已经做过的优化、测过但没有收益的尝试、对性能结构的分析，以及后续可以继续做的方向。
所有数字都注明了测量条件；没有实测的估计会明确写“估计”。

**机器：** 8x RTX 2080 Ti 22 GB（Turing，sm_75），只有 PCIe（没有 NVLink，没有 P2P），GPU0-3 在 NUMA 节点 0、
GPU4-7 在节点 1，377 GB 内存，CUDA 12.8，驱动 580.126.09。
**模型：** Qwen3.8-Flash-Next，[Unsloth Q8_0](UNSLOTH_Q8.md)，8 张卡按层切分（每张约 6 层），专家全部在显存。
**引擎：** 基于上游 Niko1221/Strata 0.1.40.3（`d5ea7133`），加上本 fork 的改动。

## 一、当前线上配置

```
"parallel": 4
args: --prefill auto --split-chunks 4 --batch-groups 4 --trim-stage-weights（另有 setup 写入的 --spec 4 --mtp 等）
env:  STRATA_BF16_TC=1, STRATA_PREFILL_ZC=1
```

部署后的线上检查（2026-10-12，提交 `5cb80b6a` 的引擎，默认 GPU 频率，单次测量）：

| 项目 | 结果 |
| --- | --- |
| 4K prompt | 1,093 tok/s |
| 16K prompt | 2,375 tok/s |
| 32K prompt | 3,234 tok/s |
| 单请求 decode（短上下文） | 61.7 tok/s |
| 4 个请求同时 | 合计 120 tok/s |
| 多轮复用 | 第二轮 8,436 token 中 8,417 个命中缓存 |

## 二、已完成的优化

| 改动 | 作用 | 实测（8x 2080 Ti，Q8_0） | 输出 |
| --- | --- | --- | --- |
| `--split-chunks 4`（新引擎参数） | 层切分时把 prompt 切成多块，各段卡同时处理不同的块 | 与 BF16_TC、线程修复一起：4K 770 → 1,120，16K 900 → 2,220，32K 850 → 2,870 tok/s（2026-10-11，原配置为 `--prefill auto:32768`） | 不变 |
| prompt 线程不再继承主线程的 CPU 绑定（`pool.cpp` `unpin_current_thread`） | 原来 35 个 prompt 线程都挤在 CPU 0 上 | 含在上一行 | 不变 |
| `STRATA_BF16_TC=1` | Turing 上 BF16 权重走张量核心 | 含在上一行 | 不变 |
| `STRATA_PREFILL_ZC=1`（零拷贝 MMQ，可选） | prompt 的专家计算直接读映射内存 | prompt +3-8% | 不逐位一致 |
| `"parallel": 4` + `--batch-groups 4` | 多个请求在各段卡之间流水线 | 8 个请求同时：合计 136 tok/s，串行 50 tok/s；优于 parallel 8 | 不变 |
| `--trim-stage-weights` | 每张卡只加载自己那几层的稠密权重 | 显存留给专家缓存，速度不变 | 不变 |
| 多列 Q8_0 MMVQ 每个 block 只读一次激活值（`native_mmvq.cu`，`c9b001b`） | verify window 3-5 列时，瓶颈在逐列读取指令 | qkv 93.5 → 79.1 µs，QSA q 111.3 → 82.9 µs，输出头 1,803 → 1,470 µs；decode 59.7 → 62.1 tok/s | 逐位一致 |
| 上游 Q8_0 稠密反量化合并写入（`dequant_bf16.cu`，`5cb80b6a`，来自上游 `e910e410`） | prompt 路径的稠密权重反量化 | 单次调用快 4-11 倍（GDN qkv 1,095 → 176 µs）；整段 prompt：4K 1,102 → 1,160，16K 2,318 → 2,333，32K 3,050 → 3,081 tok/s（各 2 次平均） | 逐位一致 |
| GPU 锁频（用户手动执行 `nvidia-smi -lgc 2000,2000`） | 默认频率下每张卡约 80% 时间空闲，计算时频率来不及升满 | 默认频率 decode 时 SM 平均只有 1,406-1,463 MHz；锁 2000 后实际 1,830-1,875 MHz，温度 52-60°C。用户反馈明显变快，**尚未做 A/B 实测** | 不变 |

## 三、测过但没有收益的

都在同一台机器、同一模型上测过（2026-10-11 至 10-12）：

- `--spec 6`：比 `--spec 4` 慢。
- `--mtp-q4`：没有收益。
- `STRATA_HC_Q8`、自写的 gr_up 预取内核：更慢。
- Strix Halo 的 8 个逐位一致开关逐个单独测：都在 ±0.5% 内；`Q8_PACKED`、`QFUSE` 慢约 3%，而且会改变输出。
- MMVQ 每个 block 算 4 行或 8 行：更慢（寄存器增多，驻留线程变少）。
- hyper-connection：新写的 up 内核（每行 8 线程）只让 up 本身快 5%；GR_V3 S=2 在本机能通过 parity 测试，但比现在用的 staged 版还慢（68.6 vs 57.7 µs）。
- GDN keyhead：输出相同，速度 0.97-1.00 倍。

## 四、性能结构

### decode（短上下文）

一个 verify window 约 48-50 ms，接受约 3-3.5 个 token。用 nsys `--cuda-graph-trace=node` 测得：

- 8 段卡串行执行，每段 5.3-6.2 ms，最后一段（含输出头）约 7.7 ms；草稿约 3.2 ms。
- 专家部分约占 41%：T=4 时每层 gate/up 274.5 µs、down 159.5 µs。gate/up 已达约 82% 带宽，down 63-73%。
- hyper-connection 读取约 78.7 µs/次，每个 window 约 7.5 ms，只用到 27% 带宽；down 内核只有 41 个 block（卡上有 68 个 SM）。
- 每个 window 约读 15.3 GB：专家 ~10 GB、稠密 ~4.6 GB、输出头 0.68 GB。按 2080 Ti 峰值 616 GB/s、8 张卡轮流算，完美内核的极限约 32-35 ms 一个 window，即约 85-90 tok/s（估计）。所以单纯重写内核最多约 1.4 倍，现实估计 +10-15%。
- 单请求 decode 在 50-70 tok/s 之间波动，主要来自草稿接受率：代码和重复内容每个 window 约 3.5 个 token，开放式文本约 3.0 个。

### decode（长上下文，线上实际负载）

线上日志（2026-10-13，混合条件）：

| 上下文 | decode |
| --- | --- |
| ~35 token | 60-62 tok/s |
| ~2.8 万 | ~54 tok/s |
| 4.4-5 万 | 40.8-42.6 tok/s |
| ~11.2 万 | 36.8-39.2 tok/s |

11 万上下文时每个 window 比短上下文多约 30 ms，这部分花在注意力和稀疏注意力的索引、选择上。之前的优化和测试都在短上下文下做，这一块还没有分析过。

### 线上用法的观察（2026-10-13 日志）

- 大部分请求是 4-11 万 token 的长对话，多轮缓存命中时 1-3 秒开始回答；4.2 万 token 的新 prompt 读了约 17 秒。
- 监控面板上 prefill 显示几十万 tok/s，是缓存命中造成的：真正新算的 token 很少。
- 有一个请求思考了 97,190 个 token（上限 139,752），跑了约 40 分钟后客户端断开，期间一直占着一个并发位置。

## 五、后续路线

### 第一组：配置或小改动，风险低

1. **锁频 A/B 与常驻**：用固定输入对比默认频率、1900、2000 MHz 的 decode 和 prompt 速度；写开机自动锁频的 systemd 服务。
2. **限制单次输出和思考的 token 上限**：防止失控请求长期占用并发位置。具体数值需要用户决定（建议思考加回答总共约 32K）。
3. **检查长对话缓存命中率**：现在 `--conversation-cache-mib 8192`。多个 agent 都在用 10 万级上下文时可能互相挤掉缓存，没命中就要把几万 token 从头重读。内存有 377 GB，加大的成本很低；先统计命中率再决定。
4. **移植上游的几个修复**：
   - 工具列表顺序变化时也能保住 prompt 缓存（#1624），直接影响 agent 场景的缓存命中；
   - head 输出出现 NaN 时自动恢复（#1892）；
   - 监听队列加大到 256；
   - 并发请求的状态记录修复（#1603、#1869、#1870）；
   - q8_1 缩放值截断（#1448、#606）、上下文末尾草稿窗口修复（`e85567b6`）、CUDA 采样的 logit bias 修复（`dcc6f756`）。

### 第二组：先测量，再决定（一个停服务 30-40 分钟的维护窗口）

5. **长上下文 decode 的 profile**（最值得做）：在 5 万和 10 万上下文下跑 nsys，看注意力、索引、选择各占多少。这些内核没有针对 Turing 调过，可能存在明显的低效。
6. **长 prompt 首次读取的 profile**：看 4 万 token 以上新 prompt 的瓶颈。候选之一是上游的 `STRATA_SPLIT_MTP_BATCH=1`（草稿层的 prompt K/V 在最后一张卡上批量计算）。
7. **长上下文下重调并发参数**：`"parallel": 4` 和 `--batch-groups 4` 是用短 prompt 测出来的。

### 第三组：较大改动，按需

8. **上游 `--pipeline-windows 2`**（3 段以上层切分，上游 `553b0b78`）：后一段卡还在验证当前 window 时，前面的卡先算下一个 window；输出和串行一致。上游在 4x RX 7900 XT 上实测 4K 上下文 decode 59.4 → 67.6 tok/s，32K 上下文 51.8 → 65.6 tok/s。不能和 `--batch` 同时用，只对单请求有意义。
9. **把整个 fork 迁移到上游 0.1.43**：试过把本 fork 的改动套到上游最新代码上，7 个文件直接套上，3 个文件共 6 处冲突，都是两边在同一位置各加了东西。因为本仓库重建过提交历史，不能直接 merge。

### 第四组：大工程，暂缓

10. **4 卡专家并行**（见下一节）：在长上下文和并发负载下收益小，prefill 会变慢。
11. **专家换成更低比特**：专家部分完全受带宽限制，换 Q6_K 估计 decode +8-10%，换 Q4 估计约 +20%，但会损失质量，还需要确认这些格式的内核在 sm_75 上的效率。

## 六、专家并行原型（2026-10-12）

**原型：** 用引擎自己的 `native_expert_grouped` 内核，随机生成 Q8_0 专家权重（512 个专家、每个 token 选 10 个、T=4）。
每张卡把 48 个 MoE 层录成一个 CUDA graph；owner 卡把量化后的输入写到映射主机内存，各卡计算自己负责的专家（expert % G），
helper 卡写回部分和，owner 按卡号顺序相加。卡之间用标志位自旋等待，每层不经过 CPU。

| 方案 | 每层专家耗时 | 一个 window（48 层） |
| --- | --- | --- |
| 1 卡（对照，引擎 profile 约 440 µs） | 426 µs | 20.5 ms |
| 2 卡 | 263 µs | 12.6 ms |
| 4 卡（同一 NUMA 节点） | 176 µs | 8.4 ms |
| 7 卡（跨 NUMA） | 156 µs | 7.5 ms |

1、2、4 卡的校验和一致。单独测的交换延迟（T=4，每层一次）：2 卡约 19 µs，4 卡约 36 µs，8 卡约 74 µs。

**推算：** 短上下文 decode 约 62 → 80 tok/s（4 卡）；4.5 万上下文约 42 → 50；11 万上下文约 38 → 44（估计）。

**暂缓的原因：**

- 并发时 `--batch-groups 4` 已经让 8 张卡同时工作，专家并行没有空闲的卡可用，只对单请求有效。
- 专家改成 4 卡分摊后，每张卡只持有自己那几层四分之一的专家，prompt 处理时需要在卡之间交换激活值。估计每个 4096 token 的块多约 0.5 秒（prompt 慢 20-30%），除非另外做重叠和压缩。
- 需要关掉 prompt 借用专家缓存、自适应专家缓存，并让 batch window 也支持。工作量估计：decode 单请求 3-5 天，prefill 再加 3-5 天。

**如果要做，改动的位置：** `src/core/verify.cpp` 里 `pre(l)` 的路由和 `resident_plan`、`post(l)` 的专家计算和合并；
`src/program/generate.cpp` 里按 stage 拆分 profile 和填充专家缓存的部分（`stage_of`、`st.profile`）以及残差表 `host_res`。
建议的做法是 helper 把每个专家的原始结果行传回 owner，按原顺序合并，这样输出和现在逐位一致（估计每层多约 20 µs 的传输）。

## 七、测量方法

- 对比测试：`/data/strata-opt/bench2080.py` 复制一份线上配置，用另一个引擎、环境变量或参数在 8091 端口启动，跑固定的
  prompt 和 decode 请求（`--fixed` 可以跨次比较输出）。测试时要先停掉线上服务，否则显存不够。
- profile：`nsys-strata.sh`（`--cuda-graph-trace=node`），再用 `kgrid.py` 按 grid 尺寸汇总内核时间。
- 逐位一致性：`STRATA_IQ_MT_MIN=1 --pcie-frac 0 --adapt-every 1000000` 下比较生成文本；内核改动另跑对应的 parity 测试。
- 部署：先等旧引擎进程完全退出，再覆盖 `engine/strata`（否则会报 "text file busy"），并保留带日期的备份。
