### 3. 持续 decode 的流水线利用率仍低

确定的代码结构：每个请求组同一时间只有一个验证窗口在流水线内；窗口依次经过 8 个阶段。
下一轮受验证结果、采样、状态提交及草稿准备的依赖约束。草稿未就绪时，调度器暂时跳过该组。
本次只有 3 个活跃组，提供的独立在途工作有限。

“同时 3 个阶段忙、8 卡平均 37.5%”只能作为简化示意，**不是这套引擎的严格利用率上限**。
MTP、输出头和 prefill 可以提供额外重叠；阶段耗时也不相等。

NVML GPU-Util 表示采样期间有内核执行的时间比例，不是 FLOPS、SM occupancy 或显存带宽利用率。
参考：[NVIDIA NVML utilization 定义](https://docs.nvidia.com/deploy/nvml-api/620/api/structnvmlUtilization__t.html)。
低活动率首先说明执行时间上有空档。单个内核是否带宽受限，需要另外测量。

**当前判断：** 低并发下流水线未充分填充，是最明确的结构性限制；窗口间反馈及主机提交也可能增加空档，尚无可靠的耗时占比排名。

### C. 代码中确认存在的机制

1. **复用的是完整匹配的前缀状态，不是任意相同文本块。**
   `conversation_prefix()` 对已保存 checkpoint 的 token 序列与请求开头做完整相等比较，并检查图像身份；
   `ConversationCache::best()` 选择满足条件的最长 live/checkpoint，且检查控制向量状态。
   请求前部若发生变化，后面即使有大量相同文本，也不能直接沿用此前那段后缀的模型状态。
   system/tool 定义、历史消息重写、思考内容重渲染、压缩/裁剪都可能改变 token 前缀；
   **这些是代码允许解释的候选原因，不是已观察到业务客户端确实发生了这些变化。**
2. **有相同前缀，还必须有那个位置可恢复的状态。**
   GDN 等运行状态和 KV、历史信息需要一致恢复，不能只截取 token 文本便任意回退。
   主会话、槽位和停放会话中的 live 状态或 checkpoint 提供恢复点；缺少更深的有效恢复点时，
   可以退到较短 checkpoint 并重新处理后续输入。
   实际进程使用 `--prompt-cache 32`，未显式指定 `--prompt-cache-every`，源码默认间隔为 16384。
   周期检查点按本次读取进度布置，也有 turn/root 等恢复点，因此复用长度不要求都是绝对 16384 的整数倍。
   `--kv-resident 32768` 是另一项存储设置，不能拿它解释所有 16384/32768 前缀回退。
3. **缓存预算不足会淘汰可恢复的完整会话状态。**
   实际配置为 131072 MiB / 256 个停放槽，物理内存保留阈值 24576 MiB。
   `ConversationCache::make_room()` 按字节和条目预算腾挪，`evict_oldest()` 跳过 pinned/guarded 条目后淘汰旧条目。
   checkpoint 链内部还有独立的保留规则，不能将它与停放会话的 256 槽混为一谈。
   这使“较深状态不在了、较短公共前缀仍可用”成为可能；但必须关联被淘汰对象才能确认某次回退由此造成。
4. **实际新增输入也会形成大量未复用 token。**
   若工具返回大文件、检索结果或新增消息确实有几万 token，就应当计算这些输入。
   缓存扩大也无法消除真正新增内容的 prefill。当前记录没有新旧请求 token 对照，无法定量拆分这一部分。
